> 版本：v0.1（立项版）｜ 2026-08-18
> 定位：跨境电商物流场景 —— 智能商品归类（HS Code）Agent 技术验证项目
> 目标：复用 flight-mcp-server 已验证的生产架构，1-2 周交付可演示的 v1.0

## 一、为什么做这个项目

### 1.1 业务背景

跨境物流中，商品归类（HS Code 归类）是报关的核心环节：

- **人工现状**：报关员凭经验查税则，一票商品归类 5-15 分钟，依赖个人经验，新人上手慢
- **错误代价**：归类错误 → 申报不实 → 海关查验、罚款、扣货、企业信用降级（AEO 认证受影响）
- **行业痛点**：税则每年调整、品目条文+类注章注+归类总规则交叉适用，纯关键词搜索工具召回质量差

### 1.2 为什么不是"直接问 LLM"

HS Code 归类是典型的**高确定性、强依据、零容忍幻觉**场景：

- 税则条文是确定知识，必须检索原文，不能让模型凭参数记忆生成
- 归类结论必须给出**可复核的依据链**（品目条文 + 类章注 + 归类总规则第几条）
- 商品描述经常信息不全（"塑料玩具"没说是电动的还是普通的），需要**主动追问澄清**再归类

这正是 **RAG + Agent + 防幻觉 + 评测体系** 的标准战场——和我简历上的核心架构能力完全同构。

### 1.3 与既有项目的关系

| 项目 | 关系 |
|---|---|
| flight-mcp-server | **架构母体**：LangGraph ReAct + MCP Tool 封装 + ChromaDB RAG + 三层防幻觉 + SQLite 记忆，直接复用骨架 |
| observable-agent-platform | **可视化复用**：SSE 思考过程可视化用于演示"Agent 如何一步步归类" |
| JH运费规则引擎 | **方法论复用**：确定性规则（正则/条件树）与 LLM 的分工边界——能走规则的绝不让模型猜 |

## 二、总体架构

```
用户（报关员/运营）
   │  自然语言商品描述："圣诞节用 LED 灯串，低压 24V，装饰用"
   ▼
┌─────────────────────────────────────────────────┐
│  FastAPI 网关层（鉴权 / 限流 / 请求日志）          │
└─────────────────────────────────────────────────┘
   ▼
┌─────────────────────────────────────────────────┐
│  LangGraph ReAct Agent（核心决策层）              │
│  ┌───────────────────────────────────────────┐  │
│  │ 规划：信息是否充分？                         │  │
│  │  ├─ 不充分 → Clarify Tool：生成追问         │  │
│  │  │   "材质是塑料还是玻璃？是否带控制器？"    │  │
│  │  └─ 充分 → 进入归类流程                     │  │
│  └───────────────────────────────────────────┘  │
│  三层记忆：工作记忆（会话状态）+ 归类历史（SQLite） │
│            + 向量长期记忆                         │
└─────────────────────────────────────────────────┘
   ▼ 工具调用（MCP Server，JSON-RPC 2.0）
┌──────────────┬──────────────┬──────────────────┐
│ Tool 1       │ Tool 2       │ Tool 3           │
│ 税则检索      │ 归类规则引擎   │ 依据链生成        │
│ (RAG)        │ (确定性)      │ (结构化输出)      │
└──────────────┴──────────────┴──────────────────┘
   ▼                ▼
┌──────────────────┐  ┌──────────────────────────┐
│ ChromaDB 税则库   │  │ 规则引擎（Python 条件树）  │
│ bge-m3 embedding │  │ · 禁限品目录正则拦截      │
│ 向量+BM25 混合检索│  │ · 归类总规则 1-6 决策树   │
│ + 重排序          │  │ · 单位/税率格式校验       │
└──────────────────┘  └──────────────────────────┘
   ▼
┌─────────────────────────────────────────────────┐
│ 输出层：三层防幻觉过滤后返回                        │
│ { hs_code, 置信度, 品目原文, 类章注引用,           │
│   归类总规则依据, 备选编码[2], 需人工复核标记 }     │
└─────────────────────────────────────────────────┘
```

### 设计决策：关键分工边界

| 环节 | 交给谁 | 理由 |
|---|---|---|
| 禁限品/危险品识别 | 正则 + 关键词表（确定性） | 合规红线，零容错，LLM 无权裁决 |
| 税则条文召回 | RAG 混合检索 | 条文是确定知识，检索优于生成 |
| 归类逻辑推理 | LLM（Agent） | 品目条文 vs 商品特征的语义匹配、总规则适用判断 |
| 最终编码输出 | 结构化输出 + 校验层 | 编码必须存在于税则库（数据库外键校验），杜绝编造编码 |
| 低置信度案件 | 标记"需人工复核" | 承认边界，比硬答更专业 |

## 三、RAG 链路设计

### 3.1 知识库构建

- **数据源**：中国海关进出口税则公开文本（示例项目用节选样例数据，约 2-3 个品目章节，覆盖常见跨境电商品类：电子配件/家居/玩具/服装）
- **切分策略**：按税则天然结构切分（品目条文为最小单元，保留"章注/类注"层级元数据），不做无脑固定长度切分——**税则条款有强结构，结构即切分**
- **元数据**：每条 chunk 挂 `{chapter, heading, subheading, code_prefix, note_type}`，支持按编码前缀过滤检索（缩小候选域，提准确率也提速度）

### 3.2 检索与生成

- **Embedding**：bge-m3（本地 Ollama 部署，与现有技术栈一致，支持中英混合商品描述）
- **混合检索**：向量召回（语义）+ BM25（编码、型号、专有名词精确命中），加权融合
- **重排序**：top-20 → 重排取 top-5 进上下文
- **num_ctx=8192**（Ollama 默认 2048/4096 会截断 RAG prompt，生产踩过的坑，本项目从第一天显式设置）
- **生成约束**：Prompt 强制"只能引用检索到的条文原文，找不到就说找不到"

### 3.3 三层防幻觉（复用并升级 flight 架构）

| 层 | 机制 | 本项目具体化 |
|---|---|---|
| 第一层：输入拦截 | 硬规则 | 禁限品正则表、明显乱码/无关输入拦截 |
| 第二层：过程约束 | RAG 交叉验证 | LLM 结论必须能映射回检索到的条文 chunk_id，映射不上即作废重试 |
| 第三层：输出兜底 | 置信度阈值 | 置信度 < 阈值 → 返回"建议人工复核 + 候选列表"，绝不硬答 |

## 四、Agent 追问机制（差异化亮点）

商品描述信息不全是归类错误的最大来源。Agent 的 ReAct 循环中内置**信息完备性检查**：

```
观察：商品描述 = "塑料玩具"
推理：归类需要 材质✓ / 是否电动? / 适用年龄? / 功能?
行动：Clarify Tool → "请问：1.是否带电动功能？2.主要供几岁以下儿童使用？"
观察：用户补充 = "电动的，给3-6岁孩子"
推理：信息充分 → 检索 9503 品目族……
```

追问问题不是自由生成，而是**由候选品目的区分特征驱动**：检索到 top 候选编码后，反向提取"区分这几个编码需要什么属性"，生成针对性追问。这是比通用聊天机器人更接近真实报关员工作方式的设计。

## 五、评测体系（对应 JD 第 6 条）

复用JH"50 组测试集拦截率 100%"的评测思路：

- **测试集**：50-100 组"商品描述 → 标准 HS Code"标注样本（从公开归类案例/税则注释例题整理）
- **指标**：
  - Top-1 准确率（8 位税号全对）
  - Top-3 命中率（候选列表含正确编码）
  - 前 4 位（品目级）准确率——品目对、子目错的场景单独统计
  - 平均响应时间 / P95 延迟
  - 防幻觉拦截率（对抗样本：编造品名、禁限品描述）
- **回归机制**：pytest 集成，每次改动自动跑评测集，指标写进 CI 报告

## 六、部署与工程化

- **推理**：Ollama 本地 qwen3:4b + bge-m3（6G 显存可跑）；预留 OpenAI 兼容接口，可切换 DeepSeek API 生成（本地 embedding + 云端生成的混合方案，已验证过）
- **服务**：FastAPI + Gunicorn（`-w 1`，SQLite 单写者约束，踩过的坑直接沿用结论）
- **部署**：Docker + docker-compose，一键起服务；GitHub Actions CI（测试 + 评测回归）
- **前端**：轻量演示页（原生 JS 或复用 observable-agent-platform 的 SSE 可视化，展示 Agent 逐步推理过程）

## 八、风险与合规声明

- 示例项目仅使用公开税则文本与自编测试样例，不含任何企业涉密数据
